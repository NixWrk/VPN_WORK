# split_tunnel.ps1

Обход активного VPN для отдельных сервисов на Windows 10/11. Скрипт определяет
физический Wi-Fi/LAN-шлюз, разрешает актуальные IPv4-адреса обслуживаемых
сервисов, ставит на них проверенные `/32`-маршруты через этот шлюз и добавляет
условные DNS-правила NRPT. Права администратора запрашивает сам.
После установки задача `SplitTunnelRouteMonitor` автоматически подхватывает
новые адреса из DNS и не даёт маршрутам протухать.

## Запуск

### Один файл: `VPN_WORK.exe`

Скачайте `VPN_WORK.exe` из [последнего релиза](https://github.com/NixWrk/VPN_WORK/releases/latest)
и запустите его двойным кликом на Windows 10/11. В главном меню есть два режима:

- **Автоматическая настройка.** Подключите свой VPN и
  подтвердите настройки. Программа применит список обхода, включит защиту
  ChatGPT и Codex и обновит уже установленный прокси Zotero, если Zotero
  закрыт. Защита использует утверждённую настройку. При первом включении она
  определяет VPN по маршрутам Windows. После перезагрузки фоновая задача
  восстановит разрешения при входе в Windows.
- **Ручная настройка.** Разделы «Обход VPN», «ChatGPT и Codex», «Zotero»,
  «Обновления программы» и «Прокси для браузера». В разделе «ChatGPT и Codex»
  можно включить защиту автоматически, выбрать один или несколько VPN вручную,
  добавить свои программы или снять защиту.

С версии 1.1 программа при обычном запуске проверяет стабильные релизы на
GitHub. Если версия новее, программа скачивает `VPN_WORK.exe`, сверяет SHA‑256
и версию и перезапускается. Начиная с 1.3.1 новый EXE сам переносит уже
включённую защиту ChatGPT и Codex при запуске, в том числе после скачивания
файла вручную. Windows запросит подтверждение UAC, если нужно обновить фоновую
задачу. При недоступном GitHub или ошибке проверки можно продолжать работу
с текущей версией. Отключить проверку и установку при запуске можно через
**Ручная настройка → Обновления программы**. Там же есть разовая проверка;
параметр `--no-update` пропускает проверку только для текущего запуска.

Для передачи на другой ПК достаточно одного `.exe`: скрипты уже внутри.
При первом запуске функции, которая устанавливает служебные файлы, Windows
запросит UAC для записи в `%ProgramFiles%\VPN_WORK`. Прокси для браузера
запускается без прав администратора. После установки служебных файлов
Планировщик запускает скрипты из установленной папки, поэтому сам `.exe` можно
переместить. Рабочие папки фоновых задач нужны до перехода на новую версию или
снятия настроек через меню.

Список адресов и дополнительные программы редактируются в соответствующих
разделах ручного режима. Эти настройки хранятся в `%LOCALAPPDATA%\VPN_WORK`.
Если раньше вы запускали скрипты напрямую,
скопируйте туда `bypass_domains.txt` и `gpt_vpn_guard.local.json`, если они у
вас были, и примените соответствующие настройки. Файлы хранятся отдельно от
пакета и не перезаписываются при обновлении.

Сборка из исходников на 64-битной Windows 10/11 не требует загрузки пакетов:

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\build_exe.ps1
.\dist\VPN_WORK.exe --verify
```

Сборка использует штатные .NET Framework и Windows PowerShell. Результат —
`dist\VPN_WORK.exe`; `--verify` выводит хеши вложенных компонентов без установки.
Номер в файле `VERSION` должен соответствовать тегу релиза (`v` и номер версии).

### Запуск PowerShell напрямую

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\split_tunnel.ps1
```

`-Remove` снимает маршруты, NRPT и фоновую задачу; `-Help` показывает справку.
Основное состояние хранится в `%LOCALAPPDATA%\split_tunnel_state.json`,
динамические маршруты — в `split_tunnel_monitor_state.json`.
Вывод последнего запуска с правами администратора сохраняется в
`%LOCALAPPDATA%\split_tunnel_apply.log` для разбора ошибок.

Перед установкой можно запустить диагностику и предварительный план без UAC и
без изменения маршрутов, DNS-правил или задач:

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\split_tunnel.ps1 -Diagnose
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\split_tunnel.ps1 -Plan
```

Диагностика показывает текущий и сохранённый шлюзы, состояние монитора,
действующую NRPT-политику, ответы DNS-кандидатов и разрешение контрольных
доменов. Строка `Apply log` показывает путь к журналу последнего применения
обхода (`%LOCALAPPDATA%\split_tunnel_apply.log`).
`-Plan` дополнительно показывает объём конфигурации; точное число
`/32` зависит от ответов DNS в момент
установки. Доступ к настройкам роутера для этих проверок не нужен.
При установке DNS-кандидат принимается только если он разрешает как обычный
контрольный домен, так и `yougile.com` и `yandex.ru`. Это предотвращает установку
правил на сервер, который отвечает лишь на общий пробный запрос.
Если `Resolve-DnsName -Server` не получает ответ,
скрипт повторяет прямой запрос штатным `nslookup.exe`. После применения NRPT он
всё равно проверяет системное разрешение доменов и откатывает новые изменения
при неудаче.

Если ни один явный сервер не проходит проверку, обход использует текущий
системный DNS Windows (`DNS mode: System`). Скрипт сохраняет маршруты для
сервисов с пригодными IPv4-адресами и перечисляет домены, чьи адреса получить
не удалось. В этом режиме скрипт не добавляет собственные NRPT-правила.
Синтетические IPv4-адреса из `198.18.0.0/15`, которые могут выдавать VPN-клиенты,
пропускаются. Для нового обхода по доменам нужен хотя бы один рабочий маршрут
к адресу сервиса.

### Запуск двойным кликом

Откройте `run_all.cmd` в Проводнике. Файл обновит маршруты через
`split_tunnel.ps1` и настроит самовосстанавливающийся SOCKS5 через
`zotero_proxy.ps1`, сообщив результат каждого шага. Сбой маршрутов не отменяет
настройку Zotero. Запрос UAC для первого скрипта ожидаем. Если Zotero уже открыт,
перезапустите его после успешной настройки прокси.

## ChatGPT и Codex: только через VPN

При первом включении достаточно выбрать **Автоматическая настройка**. После
обновления VPN_WORK переносит действующую защиту при обычном запуске EXE.
Фоновая задача сохраняет утверждённый режим, список VPN и защищённых
приложений. Снятая защита и явно отключённая фоновая задача не включаются
при обновлении. Если у старой версии без задачи в Windows сохранилась только
блокировка, VPN_WORK переносит её как есть. Вручную можно выбрать другой
режим в разделе «ChatGPT и Codex» или запустить `gpt_vpn_guard.cmd`.
Защита устанавливается отдельно от `run_all.cmd`, чтобы не прервать текущую
сессию Codex при обновлении маршрутов. Для предварительной проверки из обычного
PowerShell, без применения правил:

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\gpt_vpn_guard.ps1 -Plan
```

Автоматический режим использует типы адаптеров PPP, виртуальный туннель или
адаптер типа `propVirtual` и проверяет, что интерфейс выигрывает маршруты по
умолчанию для IPv4 или IPv6. Поддерживаются как обычный маршрут `/0`, так и
два маршрута `/1`. Если VPN работает в режиме раздельного туннелирования и
вместо маршрута по умолчанию публикует только отдельные публичные префиксы,
интерфейс принимается, когда такие маршруты покрывают обе половины диапазона
IPv4 или IPv6. Это работает без списка производителей. Для VPN, который
создаёт виртуальный Ethernet или иначе не определяется автоматически, выберите
один или несколько интерфейсов вручную. Выбор сохраняется по GUID интерфейса.
В ручном списке, `-Plan` и `-Status` показаны все обнаруженные адаптеры с
состоянием, индексом и GUID.
ZeroTier виден как виртуальная локальная сеть. Для него и других служебных
интерфейсов список показывает причину, по которой выбор недоступен. VPN в
виде расширения браузера или прокси требует отдельного способа защиты.

Windows Filtering Platform проверяет выходной интерфейс для IPv4 и IPv6,
включая TCP и UDP. Если ни один туннель не подключён, попытки выйти через Wi-Fi,
Ethernet или другой физический интерфейс блокируются. Локальный loopback
остаётся доступен для связи между компонентами Codex и входа в CLI.

Запрет сохраняется после перезапуска Windows. Временные разрешения создаёт
заново задача `VPN_WORK GPT VPN guard` при входе в Windows, смене адаптеров или
маршрутов по умолчанию, а также периодически. После временного сбоя
задача повторяет попытку через пять секунд. Код, утверждённые настройки и
журнал задачи хранятся в защищённом каталоге `%ProgramFiles%\VPN_WORK`.
До появления подходящего интерфейса внешний доступ защищённых приложений
заблокирован.

Защищаются `ChatGPT.exe`, `Codex.exe`, `Codex Web GPT.exe` и перечисленные в
скрипте отдельные компоненты Codex. Для пакетов ChatGPT и Codex из Microsoft
Store добавляются правила по идентификатору пакета. Правила по имени `.exe`
не зависят от каталога версии. Для Codex Web GPT скрипт также находит его собственный
`runtime\bun.exe` в установленных версиях. После обновления этого рантайма
повторите установку. Общие `node.exe`, `bun.exe`, `curl.exe`, интерпретаторы,
сторонние локальные прокси и запущенные Codex инструменты автоматически не
ограничиваются. Если они обращаются к OpenAI самостоятельно, добавьте
конкретный исполняемый файл в список `Programs`. Не используйте с защищёнными
приложениями локальный прокси, который выходит в интернет напрямую.

**ChatGPT в браузере.** Добавьте полный путь к `.exe` браузера в `Programs`.
Ограничение действует на весь этот браузер, включая другие вкладки и профили.
Чтобы остальные сайты работали как раньше, используйте для ChatGPT отдельный
браузер. В других браузерах доступ к `chatgpt.com` не блокируется. Проверка
домена в `bypass_domains.txt` только предотвращает конфликт маршрутов и не
заменяет защиту приложения. Служебные DNS-запросы Windows используют системную
DNS-политику; эта защита не меняет её. См. [сетевые требования ChatGPT и Codex](https://help.openai.com/en/articles/9247338-network-recommendations-for-chatgpt-errors-on-web-and-apps)
и [условия фильтрации Windows](https://learn.microsoft.com/en-us/windows/win32/fwp/filtering-condition-identifiers-).

Черновик настроек `gpt_vpn_guard.local.json` находится рядом со скриптом или
в `%LOCALAPPDATA%\VPN_WORK` при запуске из EXE. Чтобы утвердить изменения,
снова включите защиту. Задача читает утверждённую копию. Укажите `auto` для
определения VPN по маршрутам, `adapters` для списка `VpnAdapters` или `blockall`
для блокировки всех внешних соединений. Поле `VpnAdapter` поддерживается для
совместимости. Имена и GUID берутся из `Get-NetAdapter`.

```json
{
  "Mode": "auto",
  "VpnAdapters": [],
  "Programs": ["C:\\Program Files\\Mozilla Firefox\\firefox.exe"]
}
```

Чтобы выбрать один или несколько туннелей, используйте `-Guided -ChooseVpn`.
Режим `-BlockAll` сохраняет блокировку до смены режима защиты. Флаг `-NoStartup`
применяет текущие правила и удаляет фоновую задачу. После установки откройте
новую сессию ChatGPT или Codex через VPN.
Для проверки отключите VPN вне активной работы Codex: новый запрос должен
завершиться ошибкой соединения, а после подключения разрешённого туннеля снова
работать. Если запрос с VPN тоже не проходит, проверьте, какой маршрут Windows
выбирает для этого соединения и включён ли нужный туннель в защиту.
Состояние и откат из PowerShell с правами администратора:

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\gpt_vpn_guard.ps1 -Status
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\gpt_vpn_guard.ps1 -Remove
```

`-Remove` удаляет и правила, и задачу автоприменения.

## Что обслуживается

YouGile (включая автодетект шардов), Pachca, Cloud Mail / Disk-O, Zotero cloud,
сервисы Яндекса и Яндекс Диск, Bitrix24 (автодетект портала и служебных хостов десктоп-клиента),
Nextcloud (автодетект домена из `nextcloud.cfg`),
WebDAV-хосты Zotero (автодетект по всем профилям из `profiles.ini`), зоны `.ru` и `.рф`
целиком (см. ниже), NCBI/PubMed/PMC/Bookshelf, Element/Matrix и пользовательские
адреса из `bypass_domains.txt`.

### Свои адреса: штатный Блокнот

Откройте `edit_bypass.cmd` двойным кликом: он создаст рядом со скриптом файл
`bypass_domains.txt` с подсказками и откроет его в Блокноте. Права администратора
для редактирования не нужны. В PowerShell тот же редактор открывается так:

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\split_tunnel.ps1 -EditConfig
```

Одна запись на строку; пустые строки и строки, начинающиеся с `#`, игнорируются.
Пример содержимого:

```text
# Один сайт: можно вставить полную ссылку, путь и порт не ограничивают обход.
https://journal.example.org/article/123
matrix.company.example

# Зона вместе с основным доменом и всеми поддоменами.
.publisher.example
*.another-publisher.example

# Отдельный IPv4 или сеть; для сети нужен её начальный адрес.
203.0.113.10
203.0.113.0/24
```

Доменные имена на кириллице переводятся в punycode автоматически. Поддерживаются
ссылки HTTP(S)/WS(S), домены, зоны и IPv4/CIDR. Это текстовые данные, а не код
PowerShell. Для проверки без UAC и изменений сети:

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\split_tunnel.ps1 -CheckConfig
```

Сохраните файл и запустите `split_tunnel.ps1` без параметров или `run_all.cmd`.
Изменения применяются при этом запуске; фоновый монитор использует последний
успешно применённый список. Ошибочная запись останавливает установку до UAC и
изменений сети с указанием номера строки. Она не мешает работающему монитору
или удалению через `-Remove`.

Для удаления пользовательского правила уберите строку и снова примените
настройки. Удаляются его DNS-правила и больше не нужные маршруты; встроенная
зона или другой сервис всё ещё могут требовать обхода того же адреса.
`-Remove` сохраняет сам список адресов для следующей установки.
Файл индивидуален для каждого ПК и исключён из Git, поэтому обновление
скриптов не заменяет личные записи. Прежние массивы `$CustomSiteDomains` и
`$BypassDomainSuffixes` также поддерживаются.

### Научные сайты: NCBI, PubMed, PMC и Bookshelf

Сразу устанавливаются маршруты для `www.ncbi.nlm.nih.gov` (в том числе
`/books/NBK10944/`), `pubmed.ncbi.nlm.nih.gov`, `pmc.ncbi.nlm.nih.gov`, CDN и
E-utilities. Зона `.ncbi.nlm.nih.gov` получает NRPT и отслеживается монитором:
новые поддомены и их цепочки CNAME также подхватываются из DNS-кэша.
Ссылки из PubMed на сайты издателей могут вести в другие зоны — добавьте
нужного издателя в пользовательский список.

Сам по себе отказ сайта через VPN ещё не доказывает его причину: это могут быть
ограничения IP выхода VPN, DNS или маршрутизации. Добавленный обход отправляет
соединения через физическое подключение; доступность зависит и от провайдера.

### Element: индивидуальное определение на каждом ПК

Встроенный список покрывает Element Web/Desktop, стандартный сервер Matrix,
идентификацию, интеграции, загрузки, Element Call/MatrixRTC, SFU и опубликованные
STUN-узлы. Адреса сверены с
[сетевыми требованиями Element](https://docs.element.io/latest/element-cloud-documentation/element-matrix-services/domains-and-ip-addresses/),
[конфигом Element Web](https://github.com/element-hq/element-web/blob/develop/apps/web/element.io/app/config.json)
и [текущим MatrixRTC-сервисом matrix.org](https://matrix.org/.well-known/matrix/client).
Зоны `.element.io`, `.matrix.org`, `.vector.im`, `.ems.host`, `.modular.im` и
`.riot.im` отслеживаются через DNS-кэш, включая CNAME на внешние CDN.

Собственный сервер коллеги не требуется заранее вписывать в общий файл:

- При установке скрипт читает адреса из пользовательских `config.json` в
  `%APPDATA%\Element`, `Element-*`, `ElementNightly*`, `Riot` и `Riot-*`, а также
  из `ELEMENT_DESKTOP_CONFIG_JSON` и абсолютных `--config`/`--profile-dir`
  работающего приложения в текущем сеансе. Поддерживаются homeserver,
  identity server, интеграции и указанные в конфиге сервисы звонков.
  Эти пути описаны в [документации Element Desktop](https://github.com/element-hq/element-web/tree/develop/apps/desktop#user-specified-configjson).
- Каждые 3 секунды монитор находит публичные IPv4-адреса TCP-соединений
  процессов Element/ElementNightly/element-desktop/Riot текущего сеанса,
  включая попытки подключения `SynSent`, и добавляет прямые `/32`.
  Это работает и без пользовательского JSON, когда адрес аккаунта хранится
  внутри самого приложения, а также при собственном DNS клиента.
- Такие динамические адреса сохраняются до 24 часов после последнего
  наблюдения и переносятся при смене физического интерфейса. Локальные,
  частные и overlay-адреса этим механизмом не перенаправляются.

Запустите Element, примените настройки и перезапустите приложение. При первом
обнаружении нового сервера может понадобиться повторить подключение: уже
открытый сокет может оставаться привязанным к локальному адресу VPN.
`-Diagnose` показывает обнаруженные конфиги и активные публичные TCP-узлы.

Автоопределение соединений относится к настольному Element. В браузере сервер
собственной установки добавляется в `bypass_domains.txt`, если он не входит во
встроенные зоны. UDP-медиа используют тот же обход по IP, когда узел известен
из DNS, конфига или TCP-сигнализации. Адреса нестандартного TURN/SFU, полученные
только как IP по UDP, могут потребовать ручной записи IP/сети. IPv6, kill switch
и WFP-фильтрация остаются общими ограничениями решения. Маршруты Windows
действуют для всех приложений, обращающихся к тому же IP, включая общие CDN.

### Cloud Mail / Disk-O and VK

Disk-O receives some content-node IPs directly from the API, so they never
appear in the Windows DNS cache. The Cloud Mail network `95.163.51.0/24` is
therefore installed persistently from `$StaticBypassPrefixes`. VK domains and
CDN zones also bypass the VPN and are tracked by the DNS monitor. The `-Remove`
switch removes all of these managed routes.

### Яндекс Диск

В отдельную группу `Yandex Disk` входят веб-интерфейс, API, WebDAV,
загрузчик, узлы скачивания и другие опубликованные Яндексом адреса из
[сетевых настроек Яндекс 360](https://yandex.ru/support/yandex-360/business/admin/ru/network-settings).
Адреса файлового хранилища `*.storage.yandex.net` могут меняться. Монитор
добавляет маршруты к новым IPv4-адресам под уже управляемой зоной
`.yandex.net`, когда они появляются в системном DNS-кэше. Если приложение
применяет свой DNS или получает адрес напрямую по IP, такой узел потребует
отдельной настройки.

## Зоны `.ru` и `.рф` мимо VPN

### Обход с первого соединения в Edge или Chrome

Запустите `VPN_WORK.exe` обычным двойным кликом и выберите **Ручная настройка →
Прокси для браузера → Edge** или **Chrome**. Откроется отдельный профиль
браузера с доступом к локальному SOCKS5-прокси на `127.0.0.1:27655`. Этот режим
не требует предварительного применения общего обхода. Профиль сохраняется в
`%LOCALAPPDATA%\VPN_WORK\browser-proxy`. Чтобы остановить прокси, закройте окно
этого браузера и нажмите Enter в консоли VPN_WORK.

Браузер передаёт имя сайта прокси до первого TCP-соединения. Для `.ru` и `.рф`
прокси разрешает адрес и открывает сокет через физический Wi‑Fi/Ethernet, включая
IPv6 при наличии прямого маршрута и подходящего адреса сайта. Если IPv6 не
отвечает, прокси может использовать IPv4. DNS сначала запрашивается для
выбранного интерфейса. Если пригодный ответ задерживается, прокси также
обращается к системному DNS Windows. Этот запрос может пройти через VPN.
Само подключение привязано к физическому интерфейсу. Прокси принимает публичные
адреса и пропускает частные адреса и синтетические ответы VPN.

Для остальных сайтов в этом профиле действуют обычные маршруты Windows.
Домены ChatGPT/OpenAI закрыты в этом профиле. Для ChatGPT используйте обычный
браузер с включённой VPN-защитой. Системные настройки прокси и обычные профили
браузеров режим не меняет. Он охватывает веб-соединения по TCP. Если VPN
блокирует физический интерфейс, сайт из зоны `.ru` или `.рф` покажет ошибку
подключения. Имя или протокол VPN-клиента указывать не нужно.

### Общий обход через маршруты Windows

Российские сайты (`protect.gost.ru`, `uchsov.bmstu.ru`, `mf.bmstu.ru`,
`rospatent.gov.ru`, `consultant.ru` и подобные) отказывают в доступе, когда
запрос приходит с зарубежного адреса VPN. Зоны, которые нужно увести мимо VPN
целиком, перечислены в `$BypassDomainSuffixes`. По умолчанию включены `.ru` и
`.рф` (`.xn--p1ai` в DNS).

Windows не маршрутизирует по имени, только по адресу, поэтому суффикс
применяется двумя механизмами:

- **DNS.** При выборе явного резолвера скрипт ставит правило NRPT на каждую
  зону. В резервном режиме используется системный DNS Windows. Диагностика
  показывает политику обеих зон и текущий маршрут Windows для IPv4-адресов
  `yandex.ru` и `объясняем.рф`.
- **Маршруты.** `/32` создаётся только для конкретного хоста. Хосты берутся из
  `$BypassSeedDomains` (там уже перечислены домены `.gost.ru`, `.bmstu.ru`,
  `.gov.ru`, ФИПС и «КонсультантПлюс») и из DNS-кэша Windows — то есть из того,
  что этот компьютер действительно открывал. Из кэша берётся только имя; адрес
  скрипт разрешает заново сам. Установка не обрезает список известных хостов.
  Монитор распознаёт кириллицу и Punycode и проходит цепочки CNAME, в том числе
  до CDN другой зоны. Ozon, основные узлы `ozone.ru` и `объясняем.рф` включены
  в начальный список, чтобы их маршруты появились уже при применении обхода.

Практическое следствие: первый запрос к ранее неизвестному сайту зоны может уйти
в VPN. Фоновый монитор увидит адрес в DNS-кэше не позднее чем через несколько
секунд, добавит прямой маршрут, и повторная попытка приложения пойдёт напрямую.
Для сайтов из `$BypassSeedDomains` этого первого разрыва нет.

Список российских IP-диапазонов не равнозначен зонам `.ru` и `.рф`: такие сайты могут
размещаться в других странах, а один IP может обслуживать несколько доменов.
Эта схема охватывает известные имена и системный DNS-кэш. Собственный DoH
приложения скрывает запросы от монитора, поэтому гарантировать обход каждого
первого обращения к любому имени этих зон средствами этих маршрутов нельзя.

Новый сайт или зону удобнее добавлять через `edit_bypass.cmd` в
`bypass_domains.txt`: имя хоста или строкой вида `.example`. Для доменов `.ru` и `.рф`,
которые нужны сразу при установке, также можно сохранить конкретное имя в этом
списке. Встроенные `$BypassSeedDomains` сохраняют своё назначение.

## Фоновое обновление маршрутов

Успешная установка регистрирует задачу `SplitTunnelRouteMonitor` для текущего
пользователя с наивысшими правами. Задача хранит абсолютный путь к
`split_tunnel.ps1`, поэтому перед переносом файла сначала выполните `-Remove`,
а после переноса установите решение заново.

Монитор:

- проверяет DNS-кэш Windows каждые 3 секунды;
- раз в 30 секунд заново разрешает настроенные домены и недавно обнаруженные
  хосты, сохранённые в динамических маршрутах;
- при использовании явного DNS раз в 20 секунд проверяет сохранённые DNS-серверы и системный запрос
  через NRPT; после трёх подряд неудач обновляет конфигурацию, если отвечает
  запасной DNS. При полном обрыве DNS ждёт восстановления связи;
- сразу добавляет новые `/32` в активную таблицу через сохранённый LAN-шлюз;
- хранит недавно виденные динамические адреса 24 часа, чтобы пережить ротацию DNS.
- записывает отметку о работе каждые 30 секунд, даже когда шлюз недоступен;
  `-Diagnose` предупреждает, если отметка старше двух минут;
- работает непрерывно, без прежнего минутного разрыва между пятиминутными
  циклами. Планировщик поднимает завершившийся worker не позднее минуты;
- удаляет динамические адреса по сроку хранения, не вытесняя их из-за
  фиксированного лимита количества маршрутов.

Монитор заново определяет физический Wi-Fi/LAN-интерфейс в каждом цикле.
Если Windows меняет его индекс после перезагрузки или переподключения, монитор
переносит сохранённые маршруты на текущий индекс и обновляет файл состояния
без повторной установки и без ожидания DNS. Динамические адреса `.ru` и `.рф`, их
домены и сроки хранения сохраняются. При смене самого шлюза маршруты также
переносятся, затем проверяется доступность DNS. Если физический шлюз исчез,
монитор ждёт восстановления сети; интерфейс VPN не выбирается вместо него.
При недоступности сохранённых DNS-серверов он запускает обновление основной
конфигурации. При запуске с обновлённым файлом скрипта
монитор также пересобирает состояние, если в нём ещё нет новых встроенных
доменов. Смена VPN при том же Wi-Fi/LAN-шлюзе обычно не требует пересоздания
маршрутов; VPN с kill switch или фильтрацией WFP всё равно
может запретить обход. `-Remove` останавливает задачу и удаляет оба файла
состояния, динамические маршруты и журнал монитора.

Задача `SplitTunnelRouteMonitor` создаётся только после успешной установки
маршрутов, NRPT и файла состояния. Она запускается сразу, при входе текущего
пользователя в Windows и повторно каждую минуту, когда предыдущий экземпляр
завершён; при аварийном завершении Планировщик пытается перезапустить её с
интервалом 1 минута. Внутри worker опрос DNS-кэша идёт каждые 3 секунды.
Для задачи `ZoteroLocalProxy` нужен
отдельный запуск `zotero_proxy.ps1` (или `run_all.cmd`) и хотя бы один
настроенный профиль Zotero. Она также запускается сразу и при входе, повторный
триггер срабатывает каждую минуту, а настройка `IgnoreNew` не запускает второй
экземпляр, пока первый работает. Обе задачи используют абсолютные пути к
скриптам и работают только в интерактивном сеансе этого пользователя.

### Проверки разработки

Тесты используют временные файлы и подставные сетевые команды; маршруты,
DNS-правила и задачи Windows не меняются. Запуск всех проверок:

```powershell
Get-ChildItem .\tests\*.ps1 | ForEach-Object {
    & powershell.exe -NoProfile -ExecutionPolicy Bypass -File $_.FullName
    if ($LASTEXITCODE) { throw "Failed: $($_.Name)" }
}
```

## Zotero: отдельный локальный обход

Обычные `/32`-маршруты для Zotero недостаточны на машине, где одновременно
работают Red Shield VPN и ZeroTier. Zotero 9.0.6 (Gecko) мог создавать TCP-сокеты
с локальным адресом ZeroTier, хотя Windows для того же назначения выбирала
интерфейс VPN или Wi-Fi. Сокеты оставались в `SynSent`, а Zotero сообщал
`NS_ERROR_NET_TIMEOUT`.

Это подтверждено сравнением живых соединений `zotero.exe`, `curl` и .NET на одной
машине. `SkipAsSource=True`, высокая метрика ZeroTier и свежие `/32`-маршруты не
меняют выбор адреса внутри Zotero.

### Рабочее решение

`zotero_proxy.ps1` запускает SOCKS5-прокси только на `127.0.0.1`, добавляет
управляемый блок `network.proxy.*` в `user.js` зарегистрированных профилей Zotero
и создаёт задачу `ZoteroLocalProxy` для текущего пользователя. Планировщик
перезапускает proxy при сбое, а минутный повторяющийся триггер поднимает worker,
даже если Windows не классифицировала завершение как ошибку. Zotero подключается
к loopback, а наружные сокеты
создаёт .NET-клиент, который соблюдает обычную таблицу маршрутизации Windows.
Это штатный ручной SOCKS-режим Zotero, описанный в
[официальной документации](https://www.zotero.org/support/kb/socks_proxy), а не
замена или модификация WebDAV.

Установка нужна **только на проблемном компьютере**. Закройте Zotero и один раз
выполните:

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\split_tunnel.ps1
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\zotero_proxy.ps1
```

Первый скрипт обновляет маршруты и сам запрашивает права администратора. Второй
настраивает все профили из `profiles.ini`, запускает proxy и регистрирует задачу
текущего пользователя с автоматическим перезапуском при сбое. После этого
откройте Zotero. После перезагрузки Windows повторно запускать скрипт не требуется.

Пока решение установлено, не переносите `zotero_proxy.ps1`: задача планировщика
хранит его абсолютный путь. Перед переносом сначала выполните `-Remove`, затем
установите решение заново из нового каталога.

Откат (Zotero должен быть закрыт):

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\zotero_proxy.ps1 -Remove
```

### Почему это не ломает обычную синхронизацию

- Решение локально для проблемного ПК. На других компьютерах ничего устанавливать
  и менять не нужно.
- URL, логин, пароль и протокол WebDAV не меняются.
- TLS остаётся сквозным между Zotero и исходным сервером; локальный proxy не
  расшифровывает содержимое.
- Через proxy проходят обычные запросы Zotero к `api.zotero.org`, WebDAV и другим
  HTTPS-ресурсам. Сервер видит стандартного клиента Zotero.
- Proxy слушает только `127.0.0.1`, недоступен из локальной сети и не требует
  сторонних программ.
- Задача `ZoteroLocalProxy` работает только в сеансе текущего пользователя и
  повторно запускает отсутствующий worker не позднее чем через минуту.
- `-Remove` останавливает только созданный proxy и восстанавливает предыдущие
  строки `network.proxy.*` каждого профиля.

На проверочной машине Zotero через прокси установил соединения к API через VPN
и к WebDAV через Wi-Fi. Синхронизация завершилась, а `zotero.exe` обращался
только к loopback.

## Red Shield: почему DNS остаётся в VPN

При проверке с включённым Red Shield DNS-запросы к локальному роутеру,
`8.8.8.8` и `1.1.1.1` через Wi-Fi не проходили, тогда как
`8.8.8.8` и `1.1.1.1` отвечали по маршруту VPN. В состоянии Windows Filtering
Platform обнаружены блокирующие фильтры для порта 53 и отдельное разрешение
для процесса Red Shield `rsvdnsleak.exe`. При этом через Wi-Fi работали порт 80
роутера и HTTPS (порт 443) к обоим публичным адресам. Значит, наблюдаемый
отказ прямого DNS вызван локальной защитой от утечки DNS, а не ошибкой `/32`
маршрутов.

Пока защита включена, DNS-запросы управляемых сервисов могут проходить через
VPN, хотя проверенное TCP-соединение к Яндекс WebDAV идёт напрямую через
Wi-Fi. Если DNS через VPN недоступен, новые соединения могут задерживаться
или не открываться. Маршруты Windows не отменяют фильтры WFP; для прямого DNS
нужно отдельно менять DNS-политику VPN. Скрипт эту защиту не отключает.

## Ограничения маршрутизации `split_tunnel.ps1`

- **DNS через VPN.** Сначала проверяются DNS-серверы физического адаптера,
  затем публичные DNS через LAN. Если они недоступны напрямую, проверяются
  публичные DNS по текущему маршруту и DNS активного VPN-адаптера. В последних
  двух режимах ответы могут зависеть от VPN; NRPT задаёт сервер, но не способ
  доставки пакетов. Скрипт проверяет DNS и прямым запросом, и через временное
  NRPT-правило: OpenVPN может пропускать первый способ и блокировать второй.
  Если эти проверки не проходят ни для одного сервера, используется системный DNS.
- **Только IPv4.** Резолвятся исключительно A-записи. Если сервис доступен по
  IPv6, трафик уйдёт в VPN.
- **Динамические `/32`.** Адреса сервисов могут меняться за секунды. Монитор
  обновляет известные домены каждые 30 секунд, ловит фактически использованные
  адреса в DNS-кэше каждые 3 секунды и удерживает их 24 часа. Ручной повторный
  запуск обычно не нужен после смены VPN или ротации адресов сервиса: монитор
  обновляет маршруты и проверяет смену физического шлюза автоматически.
- **VPN с kill switch или WFP-фильтрацией** обходится не маршрутами: фильтры
  работают ниже таблицы маршрутизации. Два одновременно включённых VPN,
  направляющих весь трафик через одинаковые маршруты `0.0.0.0/1` и
  `128.0.0.0/1`, могут конфликтовать; проверяйте их по одному.
- **Корпоративные GPO/NRPT, собственный DoH приложения, IPv6-only endpoint**
  могут переопределить создаваемые правила.
- **Суффикс из `$BypassDomainSuffixes` покрывает зону целиком только по DNS.**
  Маршрут получает лишь тот хост, который уже известен по имени: из
  `$BypassSeedDomains` или из DNS-кэша Windows. Первый запрос к новому сайту
  зоны может уйти через VPN; монитор добавляет маршрут для повторной попытки
  не позднее чем через несколько секунд.
- **Внутренние имена той же зоны.** Если во внутренней сети используются имена
  обходимой зоны (например, домен `corp.company.ru`), правило NRPT уведёт их на
  публичный резолвер. На доменных машинах такой суффикс задавать не следует.

## Смежная находка: длинные sidecar-пути Zotero Worker

Эта ошибка не связана с VPN или WebDAV. Локальный `zotero-worker` раньше писал
рядом с обработанным HTML служебный файл
`<полное-имя>.html.zotero-html-provenance.json`. Сам Zotero этот файл не создаёт
и не хранит ссылку на него в SQLite, но включает все файлы каталога вложения в
архив WebDAV. На Windows Zotero 9.0.6 не может выполнить `stat` для такого файла,
если полный путь достиг 260 символов, и сообщает:

```text
Could not stat ...zotero-html-provenance.json: file does not exist
(NS_ERROR_FILE_NOT_FOUND)
```

Файл при этом существует. `LongPathsEnabled = 1` не исправляет ограничение в
используемом Zotero/Gecko файловом API.

Исправление находится в producer-е: `zotero-worker` теперь всегда использует
короткое имя `zotero-html-provenance.json` внутри каталога вложения. Чтение
старого имени оставлено как обратная совместимость. Поэтому не меняются имя
основного HTML, ключ вложения, база Zotero, URL WebDAV или формат синхронизации.

Для уже обработанных библиотек достаточно один раз переименовать только эти
служебные sidecar-файлы при закрытом Zotero. Основные HTML/PDF вручную
переименовывать нельзя. После миграции на проверочной машине не осталось
путей длиной 260 символов и более, а синхронизация через WebDAV завершилась.

Проверить библиотеку без изменений:
